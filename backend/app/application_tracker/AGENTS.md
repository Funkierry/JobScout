# Application tracker

### Application tracker browser navigation

`store.py` also owns JobScout target roles, links to prep/match threads and tracker applications, and a bounded per-thread match-candidate snapshot. Preserve per-user ownership checks in both store and Gateway routes; a thread or application may link to at most one target. Deleting a target must leave the underlying thread and application intact. A Feishu target's table and record IDs identify the source, but its private JD snapshot is user-supplied context, never public research evidence. Tracker application URLs remain separate personal official-status URLs and must not be inferred from a Feishu role URL.
The application tracker in `app/application_tracker/` first extracts from the registered URL. When that result is unknown or low-confidence, it may click one recognized read-only application-list tab (such as “我的投递”) and extract again from the new page. Its agent can also click bounded read-only refs; after a click, rerun structured extraction so multi-role listings are retained. Keep the browser's interactive-element selectors, the toolbox click allow/deny lists, and the workflow's navigation/re-extraction tests aligned. Never treat a successful page read as proof that a role or status was found, and never allow submission/withdrawal actions through this navigation path.
Broad active wording such as “进行中” is a conservative alias for the existing `简历筛选` bucket only when grounded evidence identifies the current application and contains no more specific or terminal stage. `status_semantics.py` is shared by structured extraction and agent updates; keep its confidence cap, original-page excerpts, and multi-role behavior covered by tests. This bucket does not assert that résumé review has actually begun.
Application dates come from the recruitment page, not the add form. `dates.py` verifies a proposed absolute date against a verbatim, submission-specific excerpt and rejects deadlines, posting dates, and future dates; the extractor and agent tool share it. `store.py` persists `applied_at_evidence` through a backward-compatible SQLite column migration, updates each discovered role's date independently, and preserves a known date when a later page omits it. The standalone web table derives current-stage wait from `changed_at` only as a first-observed lower bound; manual stages do not inherit that estimate.
Stage 0 baseline artifacts are private: `scripts/application_tracker_snapshot.py` reuses the hashed persistent profile and network guard, and saves raw page text/screenshot plus bounded redacted XHR/fetch JSON only under gitignored `local_eval/tracker_snapshots/`. The annotation and explicit model-cost baseline scripts operate on that local directory. Keep real page content, labels, and evaluation records out of tracked files and logs; `docs/jobscout/metrics.md` contains only actual aggregate numbers or “待运行”.

Stage 4: `observations.py` shares bounded response reading/redaction with snapshots; runtime same-host JSON records precede denoised DOM. `confidence.py` owns rule scoring for extractor and agent updates, including per-role evidence/date boundaries and current-status conflicts. Screenshot-only evidence cannot confirm a status. `browser/observation.py` bounds navigation settling; clicks require fresh stable-body samples. Interactive checks start headed and reuse one context; batches disable login handoff. Browser profile locks span request factories in one loop. `update_service.py` serializes each host group with bounded cross-host workers and cancellation cleanup; SSE completed counts must remain monotonic despite out-of-order rows. Keep tests synthetic and real replay metadata private; see `docs/jobscout/tracker-stability.md`.

Stage 5: `adapters/` parses only captured JSON from exact verified ATS hosts and API paths. Feishu/ByteDance, Tencent and Xiaohongshu mappings are pilot-derived, not vendor-wide status dictionaries. Unknown codes, ambiguous roles, incomplete lists and failed latest responses fall back. Browser/toolbox carry bounded, redacted `json_responses` separately from model-visible observations; never expose the full envelope in a tool payload. `ApplicationTrackerAgent.from_model_name` is lazy and creates fallback model/extractor state per run; both initial and post-click extraction try adapters first. Keep no-model-hit, fallback, navigation freshness and synthetic schema tests. `application_tracker_adapters_eval.py` uses the same production dispatch, frozen labels only for scoring, and private outputs; it never invokes fallback. Report coverage separately from accepted accuracy, and distinguish pilot replay from independent evaluation. See `docs/jobscout/ats-adapters.md`.

Stage 6: `email/` is opt-in and has no model calls. Local credentials are never returned by the Gateway. Gmail uses readonly OAuth; IMAP uses EXAMINE and BODY.PEEK, never flag mutations or mail sending. Filter exact sender domains and subject keywords before reading bodies. Mail events live in a separate owner-scoped ledger; the store's `source_summary` is a derived display view and must not overwrite portal history or the input to its extractor. Receipt time, appointment time, and portal observation time are distinct. Ambiguous company/role matches, negated/quoted templates and terminal conflicts require review. Use private local files and synthetic MIME/transport tests; see `docs/jobscout/mail-channel.md`.
