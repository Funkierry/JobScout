# 定时刷新与站内通知

阶段 7 复用 DeerFlow 的 scheduler、任务存储、租约与运行生命周期。JobScout 只增加专用 assistant `jobscout-tracker-refresh`；它不组装主 agent，且只接受服务器内部调度上下文、匹配当前用户的任务 ID 和运行 ID。普通对话不能直接触发这个入口。

## 启用

默认关闭，以下操作由使用者自行执行，会访问本人已授权的招聘页面：

1. 在本地 `config.yaml` 设置 `scheduler.enabled: true`。
2. 在启动 Gateway 的环境设置 `JOBSCOUT_SCHEDULED_REFRESH_ENABLED=1`，重启 Gateway。
3. 在投递进度的「定时刷新」中启用，设置间隔、每日上限与额度重置时区。

PowerShell 环境变量示例（不要自动执行）：

```powershell
$env:JOBSCOUT_SCHEDULED_REFRESH_ENABLED = "1"
# 使用项目的本地启动命令启动 Gateway
```

默认间隔 360 分钟，范围 60–10080 分钟；默认每日 30 次，上限 100 次。额度以**每个用户、每个申请条目**计数，登录失败、抓取失败和取消也占一次。实际检查前使用 SQLite 原子事务扣减；同一调度运行与申请的组合只计一次，重启不清零。同一申请也受最小间隔约束。首次执行在保存后的一个间隔，优先检查最久未更新的非终态记录；终态记录跳过。

后台检查串行，复用已有持久化登录 profile，不打开交互登录窗口，不点击投递、撤回或提交。过期登录需用户回到单条刷新处理。手动刷新沿用原来的按域名限量并发，它不受本功能每日额度控制；这里不是全站所有请求的总限流器。

「允许模型回退」默认关闭：只尝试 ATS 确定性解析，失败则保留未完成结果，不初始化模型。用户勾选后才允许既有模型流程，可能产生费用。此开关只控制定时刷新，不改变手动检查行为。

## 暂停与恢复

关闭用户开关会立即阻止后续额度预留。正在检查的单条任务允许完成；如果 scheduler 已有执行中的租约，接口会提示在当前检查结束后再保存一次，以暂停原生调度任务。等待中的任务使用 scheduler 自带的原子取消机制。不修改上游的运行租约规则。

服务器开关关闭后，专用图拒绝运行；恢复服务器开关与用户设置后，继续复用原任务。修改频率遇到执行中的任务会返回冲突，不会并行创建第二个刷新任务。

## 通知

站内通知包含公司、岗位、旧状态、新状态、逐字证据、来源与检查/收件对应的时间。官网成功检查中的已知状态变化与邮件合并后明确采用的状态变化，会和结果在同一 SQLite 事务持久化。首次识别、相同状态、未知、失败结果和邮件冲突不通知；重复邮件与重复写入不重复通知。

通知与已读状态按用户隔离，界面展示最近 100 条。停留在可见的投递界面时每 60 秒读取站内通知；不调用模型或邮箱。刷新列表后也更新未读数。邮件和其他外发通知尚未接入，系统不会发邮件。

API（需要登录）：

- `GET /api/jobscout/tracker/schedule`：设置、服务器开关、当日用量、下一次执行时间。
- `PUT /api/jobscout/tracker/schedule`：保存设置并创建/更新/暂停原生任务。
- `GET /api/jobscout/tracker/notifications`：当前用户最近通知。
- `POST /api/jobscout/tracker/notifications/{id}/read`：只修改本人通知。

数据只存本地 tracker 数据库；调度运行的对话输出只含计数，不携带邮箱内容、公司岗位或状态证据。真实周期刷新效果待用户主动启用后验证；离线结果见 [metrics.md](metrics.md)。
