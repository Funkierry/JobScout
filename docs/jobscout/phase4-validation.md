# 第四阶段：反馈复验、流程验证与展示

日期：2026-10-22。基线：`d25d2d71`。本轮先检查实际数据，再从可复现的问题出发。当前实例尚无用户保存的反馈或准备笔记，没有开展真实多人试用，不能宣称收到了试用反馈或改善了求职结果。

## 发现与修复

| 可复现的问题 | 修复后的行为 |
|---|---|
| 面试标签即使置信度低、没有检查时间或检查失败，也会进入“准备下一轮” | 先提示补充或核对状态依据；用户手动阶段、有效邮件和其他优先项继续按原规则处理 |
| 反馈只能取最近 50 条，旧记录不可访问 | 按编号读取更早记录，保留失败前已读内容；界面和导出范围显示已读数量 |
| 新建更正无法明确关联原反馈 | 从原记录追加复验，保留账号/资源/报告版本关联及用户确认结论；原记录不可覆盖 |
| 部署检查未实际请求 workbench.js | 容器 smoke 增加该资产请求，防止发布包遗漏模块 |

后端先增加回归测试，修复前为 5 失败、13 通过，修复后 18 项通过。其余未失败的新增用例覆盖旧载荷兼容和非法复验输入。完整测试结果见 [metrics](metrics.md)。

## 可重复的流程验收

使用生产界面、FastAPI 路由、Pydantic 校验和临时 SQLite；浏览器所有请求拦截，无真实模型、招聘网站、邮箱调用。账号身份与报告历史使用合成 fixture，因此这是覆盖该流程的离线集成验收，不是完整线上业务效果评测。

```bash
cd backend
uv run --no-sync python scripts/jobscout_offline_tests.py \
  --test ../jobscout-web/test_journey.py \
  --junitxml ../local_eval/ci/journey.xml
```

需要已有 Playwright Chromium。CI 在安装锁定依赖和浏览器后运行，上传 JUnit、合成截图和结果 JSON。JSON 包含提交、工作区是否修改、fixture 哈希、Python/浏览器版本及实际耗时；耗时是本机/CI 测试执行时间，不是用户任务延迟。

该流程实际执行：

1. 低置信度的合成面试记录 → 工作台核对入口 → 识别纠错。
2. 保存反馈 → 从原编号记录复验 → 保存用户确认的实际结果。
3. 读取更早记录失败 → 重试 → 共读取并导出 53 条，检查无重复及关联字段。
4. 打开合成匹配报告 → 保存一项准备和笔记 → 重建存储对象、刷新页面 → 恢复笔记。
5. 校验投递事实未变；另一账号不能读取记录、准备笔记或引用原反馈；非法页大小/游标被拒绝。
6. 桌面与 390px 手机宽度检查，页面无未处理脚本错误或意外外部请求。

原有 `test_workbench.py` 继续验证保存失败、响应丢失重试、并发修改冲突、退出后的迟到响应隔离。状态、匹配与证据质量边界由完整专项覆盖，不能由单个演示流程替代。

## 演示顺序

在测试或演示账号中使用明确标注的合成材料，避免往真实投递记录写入测试反馈。

1. **说明判断边界。** 展示“进行中·具体阶段未知”和低置信度核对入口，打开原文；不要展示虚构的“匹配概率”。
2. **从报告走到动作。** 打开通过证据门槛的匹配/准备报告，对照 JD 与简历原文，勾选一项准备、填写个人笔记并保存，重新打开确认恢复。
3. **让问题可复验。** 保存“原结果—实际结果—原因—复验条件”，从编号追加复验，展示原记录仍在、复验有独立结论；读取更早历史并导出。
4. **展示工程证据。** 展示该提交的 CI 和本地结果；指出合成测试不代表真实模型准确率、真实试用人数或求职成效。
