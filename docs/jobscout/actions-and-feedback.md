# 准备行动与反馈（复盘第三阶段）

日期：2026-10-22。基线：`1daf9a2d`。本阶段把已有投递事实和证据报告连接到用户的实际准备动作，保留原有表格与证据边界。

## 工作台待处理事项

展开“待处理事项”即可查看全部投递记录中的来源冲突、需要登录、未读进度变化、测评/笔试/面试准备，以及未知或失败的状态检查。目标岗位缺少 JD 时也会提示补充。事项按上述类型排序，每组最多 6 条，支持翻页，不根据当前投递表格页计算总数，也不猜测截止时间或面试时间。

“查看并处理”打开该记录的来源详情，即使记录不在当前表格页；“查看变化”打开已有通知；“继续准备”打开关联岗位，未关联时先保存目标岗位。补充材料进入岗位准备对话。读取事项不会启动招聘网站、邮箱或模型调用。通知标为已读后会更新事项列表。

## 从报告到准备进度

新准备报告在原有“证据边界与后续建议”内增加准备行动，最多选取 3 条已校验的差距、必备要求或职责原文，保留来源；只有已有简历原文时才展示个人经历。缺材料时明确提示补充，不编写经历。匹配报告补充核对缺项、整理真实经历和推荐决策的顺序。顺序是准备建议，不是公司面试安排或考试概率。

通过现有证据校验的报告下方有独立准备区：核对要求、整理经历、练习或完成决策三项，以及个人经历和待补材料笔记。只有用户明确保存才写入进度；浏览页面不记为完成。笔记按用户、对话和报告内容摘要隔离，新报告不会继承旧报告的勾选。刷新后可恢复同一版本的笔记。两页同时编辑时拒绝覆盖新版本；失败保留内容供重试。

报告的 Markdown/PDF 仍只包含报告本身，不自动带入私人笔记。笔记摘要使用浏览器 Web Crypto，支持 HTTPS 和 localhost；不安全的远程 HTTP 上会说明无法读取笔记，报告仍可查看。现有旧报告的证据门槛保持不变，不会因为增加准备区而绕过校验。

## 最小反馈与试用记录

工作台提供“反馈与试用记录”，识别详情提供“记录识别纠错”，报告提供“记录报告反馈 / 推荐决策”。可填写记录类别、问题类型、原结果或试用任务、更正或实际结果、原因或阻塞点、下次复验项，并记录接受/放弃推荐、任务完成/受阻。

记录保存在当前账号，默认读取最近 50 条，可继续读取更早记录，JSON 导出只包含界面已读取的数量。同一提交丢失响应后重试不会重复写入，版本升级后的旧记录重试也保持去重。用户纠错与官网事实分开保存，不自动改写阶段、原文、历史或匹配结论，也不自动回灌提示词。线程删除同时清理该线程的准备笔记和反馈；删除投递记录会级联删除其反馈。反馈不提供覆盖式修改；第四阶段新增“记录复验”，追加与原记录关联的实际结果及用户确认结论，保持相同账号、投递/对话和报告版本。

第四阶段同时修正待处理事项：仅有低置信度、未检查或检查失败的官网面试状态先核对依据，不直接提示准备下一轮。已明确手动确认的阶段和有效邮件来源保留原来的处理方式。详见[第四阶段验证](phase4-validation.md)。

## 5—8 人试用执行方式

本次交付的是记录入口及验证过的流程，**尚未开展 5—8 人真实试用**。后续由实例管理员邀请试用者，各自使用独立账号，在真实任务中记录：

1. 查看一次真实投递变化或恢复一次登录，说明结果是否得到原文支持。
2. 选择一个目标岗位，查看报告，完成至少一项准备，并保存真实经历或待补材料。
3. 对一项推荐记录接受/放弃原因；发现问题时保留原结果、更正依据和复验条件。
4. 使用“试用任务记录”记录完成或受阻，以及阻塞原因。不要填写凭据或复制他人隐私。

只有实际完成的有效求职动作才可用于后续产品评估。当前勾选是用户自报，反馈条数不是试用人数或成功率；尚未实现跨账号统计、人工质量标注和真实效果评价。不要把合成测试通过数当作用户收益。

## 开发验证

后端 `test_jobscout_workbench.py` 覆盖 owner/report 隔离、revision 冲突、重试去重、线程清理、全量分页与事实不变；原有专项测试继续运行。前端六个入口包括新增 `test_workbench.py`，使用生产笔记存储与临时 SQLite、拦截全部 HTTP 请求，验证保存/恢复、丢失响应重试、导出、移动端和退出隔离。Docker 明确复制新模块，CI 运行该新测试。

实现新增 `jobscout_prep_plans`、`jobscout_feedback` 两表，不改写已有投递事实。上线前备份原数据库，确认最终提交的所有 GitHub workflows 成功后再重启 Gateway，并检查健康、登录态界面和原记录保持情况。实际测试结果见 [metrics.md](metrics.md)。
