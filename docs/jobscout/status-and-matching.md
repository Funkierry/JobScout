# 状态表达与岗位匹配修复（2026-10-22）

本次为项目复盘后的第一阶段修复，基于 `6c4e5689`。此前阶段 0–7 的编号保持不变；PRD V1.0 仍是 2026-10-19 的历史评审快照。改动仅在 JobScout 应用、独立界面、技能契约与测试中，不改 DeerFlow 通用运行时。

## 状态如何表达

| 观察 | 当前展示 / 行为 |
|---|---|
| 当前申请原文只有“进行中 / 处理中 / 审核中”等 | `进行中·具体阶段未知`；进入待核对；不推断简历筛选，不计算当前阶段等待时间 |
| 原文明确“简历审核 / 简历筛选” | 保留 `简历筛选` |
| 有可核对的官网或邮件原文 | 展示依据状态及原文，不显示“95% / 100% 置信度” |
| 来源冲突、登录失效、读取失败或证据不足 | 分别提示核对、登录或检查未完成 |

API 保留 `confidence` 以兼容现有消费者；它是规则分，用于检查策略，不是正确概率。邮件显示也不再把来源选择时的内部值呈现为 100%。

数据库初始化时，仅对旧 `简历筛选` 中有当前申请原文、且没有具体阶段信息的记录作幂等纠正。保持 `checked_at`、`changed_at`、历史检查和人工阶段；修正自动阶段并递增 revision，阻止迁移前启动的刷新覆盖新状态。不新增检查或通知。缺少证据列的早期不完整表不做推断。下次相同结果不产生假变化；从模糊进度到明确阶段仍可通知。

登录后的本地验证发现，历史证据可能只保留 `"statusInfoCN": "进行中",`，没有周围的页面标签。归类和迁移现已支持这一明确字段，其值必须与原始状态一致；相似字段名、其他字段里的“进行中”、或同时出现的明确简历阶段不能触发这一分支。新增测试同时覆盖实时 JSON 观察与历史数据迁移。

## 岗位推荐如何校验

每个计分项除原有维度、分值和简历文件/片段外，还须提供：

- `requirement_field`：该岗位快照中的具体要求字段；公司名、备注或链接不能冒充要求。
- `requirement_quote`：在该字段中逐字存在的岗位要求。
- `matched_term`：同时存在于两侧原文的有效对应词；不能仅用“项目 / 经验 / 能力”等泛词，Go 也不能命中 Django。

保留 30/30/20/10/10 的五维上限与代码求和、稳定排序。重复维度或跨维度复用同一规范化简历片段不计分；技能片段不能充当学历，明确否定或仅计划学习的片段不计分。明确的学历/经验最低门槛与简历可比较信息冲突时，岗位不入榜；“优先”等偏好不是硬门槛，多学历选项与经验区间不能错误取最高值。缺失信息保留为待核对，不当作不符合。

总分为零的岗位不入榜，最多推荐 10 个。没有可推荐岗位时明确返回“没有通过双侧证据校验的推荐岗位”，评测器允许这一结果，不强制凑数。报告同时展示岗位原文、简历原文、对应词、待核对维度和剔除数量；依据分表示当前证据下的排序，分值仍由模型建议，不是匹配率或录用概率。

服务器证据标记新增 `match_contract_version=1`。没有该标记的旧匹配报告在实时展示、历史回放、打印和下载时提示重新生成；旧会话仍保留。面试准备的证据版本不变。

## 验证与边界

合成测试覆盖模糊/明确状态、旧库及手动阶段、迁移幂等与通知、前后端计数、浏览器详情、两侧引文/记录隔离、重复片段、零推荐、学历/经验冲突和偏好/区间、旧报告拦截，以及生产模板与离线评测重放一致性。实际运行结果见 [metrics.md](metrics.md)。

这些有限规则不能证明完整语义匹配，也不能覆盖所有学历表述、工作年限写法、地点偏好或硬性要求。同义词、别名和特殊字段名可能无法计分；未知或无法明确比较的要求仍需人工复核。本轮不增加模型调用，也未运行真实网站、模型或邮件实验；不把合成回归通过写成真实准确率提升。

更新代码后重启 Gateway 并刷新独立界面，首次初始化会执行迁移；历史匹配评分需重新生成。按常规升级流程保留数据库备份，不应在同一数据库上混跑新旧 Gateway。
